# 05 — Admin Portal

The admin portal serves `ADMIN`-role users (FDB Bank operations, compliance, product
teams). It is the control plane: monitoring, KYC/AML, user & merchant management, and
audit.

- **Frontend**: `frontend/src/pages/{admin,audit,disputes,support}/...`
- **API client**: `adminApi`, `auditApi`, `disputeApi`, `supportApi` in
  `frontend/src/services/api.ts`
- **Routes**: `/admin /admin/kyc /admin/aml /admin/users /admin/merchants /audit`
  `/disputes` (All tab) `/support` (Manager view)

Admin endpoints are spread across **several services** and the gateway routes them by
path prefix (see [README §3](./README.md)):
`/v1/admin/kyc/**` → kyc-service, `/v1/admin/aml/**` → fraud-risk-service,
`/v1/admin/users/**` → auth-service, `/v1/admin/merchants/**` → merchant-service, and
the remaining `/v1/admin/**` (dashboard) → reporting-service.

---

## 1. Dashboard — `/admin`

**What it is.** Platform KPIs and quick links to review queues.

**How it works.**
- `GET /v1/admin/dashboard` → reporting-service `/admin/dashboard` (KPI payload).
- `GET /v1/admin/kyc/pending` (kyc-service), `GET /v1/admin/aml/alerts`
  (fraud-risk-service), `GET /v1/disputes/stats` (dispute-service) drive the "review
  queue" cards that deep-link into the respective pages.
- A "system health" panel (API Gateway, DB, Kafka, Redis) is **hardcoded** in the UI —
  not API-driven.

**Cross-portal integration.** The dashboard aggregates data produced by every other
portal: transactions (customer transfers, merchant payments, payroll), users (all roles),
KYC submissions, AML alerts and open disputes. reporting-service caches derived figures
in `report_cache`.

**Backend**: reporting-service `ReportingController` (`/admin/**`).
**Data**: `report_cache` (fdbpay_reporting) + aggregates from wallet/transfer.

---

## 2. KYC review — `/admin/kyc`

**What it is.** Review KYC submissions and approve/reject customer tier upgrades.

**How it works.**
- `GET /v1/admin/kyc/pending?page=&size=&status=` → kyc-service `/admin/kyc/pending`
  (submissions + document info).
- `PUT /v1/admin/kyc/{id}/review` `{status: VERIFIED|REJECTED, reason?}` → kyc-service
  `/admin/kyc/{id}/review`. Rejection requires a reason.
- UI: status filter tabs (PENDING/VERIFIED/REJECTED/ALL), paginated table, approve/reject
  modals, toast feedback.

**Cross-portal integration.** This is the admin half of the customer KYC workflow: when
approved, the customer's `kycTier`/status upgrades in auth-service, `kyc.reviewed` is
published (audit-service consumes it), and the customer is notified. Document files are
stored in MongoDB by kyc-service.

**Backend**: kyc-service `AdminKycController` (`/admin/kyc/**`).
**Data**: `kyc_submissions`, `kyc_documents` (fdbpay_kyc), docs in MongoDB.

---

## 3. AML alerts — `/admin/aml`

**What it is.** Review fraud/AML alerts raised by the risk engine and act on them.

**How it works.**
- `GET /v1/admin/aml/alerts?severity=&status=&page=` → fraud-risk-service
  `/admin/aml/alerts`.
- `POST /v1/admin/aml/{id}/action` `{action: DISMISS|INVESTIGATE|RESOLVE, reason?}` →
  fraud-risk-service `/admin/aml/{id}/action`.
- UI: severity/status filter chips, paginated alerts, action modal.

**Cross-portal integration.** Alerts are generated by fraud-risk-service from
`txn.completed` and AML screening of platform transactions (originating from all
portals). Resolution actions feed the audit trail. The `fraud_alerts` table stores the
queue.

**Backend**: fraud-risk-service `AdminAmlController` (`/admin/aml/**`).
**Data**: `fraud_alerts` (fdbpay_fraud_risk).

---

## 4. User management — `/admin/users`

**What it is.** Search users and suspend/activate them.

**How it works.**
- `GET /v1/admin/users?search=&status=&page=` → auth-service `/admin/users`.
- `PUT /v1/admin/users/{id}/status` `{status, reason?}` → auth-service
  `/admin/users/{id}/status`.
- UI: search by phone/name, status filter chips, paginated table, detail modal, and a
  suspend/activate modal with reason.

**Cross-portal integration.** Users here span **all five roles** (auth-service owns the
`users` table). Suspending a user blocks their portal session/transactions platform-wide
since every service trusts the JWT tied to that user and wallet-service respects user
status. User status changes are audited.

**Backend**: auth-service `AdminUserController` (`/admin/users/**`).
**Data**: `users` (fdbpay_auth).

---

## 5. Merchant management — `/admin/merchants`

**What it is.** Approve, suspend or activate merchants.

**How it works.**
- `GET /v1/admin/merchants?search=&status=&page=` → merchant-service
  `/admin/merchants`.
- `PUT /v1/admin/merchants/{id}/status` `{status, reason?}` → merchant-service
  `/admin/merchants/{id}/status`.
- UI: search + status filter chips, paginated table, detail modal (business type,
  category, address, settlement type, fee schedule), approve/suspend/activate modal.

**Cross-portal integration.** Approving a `PENDING` merchant activates its wallet and
makes it visible in the **customer** Merchant Directory and scannable via QR; suspending
one blocks new payments to it. Merchant status drives the merchant portal login/QR
behaviour and is audited.

**Backend**: merchant-service `AdminMerchantController` (`/admin/merchants/**`).
**Data**: `merchants` (fdbpay_merchant).

---

## 6. Audit log — `/audit`

**What it is.** Immutable, append-only log of platform events with filters and export.

**How it works.**
- `GET /v1/audit/log?actor=&action=&resourceType=&resourceId=&from=&to=` → audit-service
  `/audit/log` (Page).
- `GET /v1/audit/resource?resourceType=&resourceId=` → per-resource history.
- `GET /v1/audit/summary` → `{ totalEvents, uniqueActors, topActions[] }`.
- `GET /v1/audit/export?format=csv|json` → file download.
- UI: summary cards, filter form, events table, CSV/JSON export.

**Cross-portal integration.** audit-service is a **consumer** of the platform event
stream: `txn.completed`, `kyc.reviewed`, `dispute.created/resolved`,
`settlement.completed`, `audit.log`. Every portal action therefore lands here
automatically, giving admins an end-to-end trail across customer, merchant, agent and
corporate activity.

**Backend**: audit-service `AuditController` (`/audit/**`).
**Data**: `audit_entries` (fdbpay_audit).

---

## 7. Disputes (admin view) — `/disputes`

Admins open the "All Disputes" tab (via `GET /v1/disputes/all`) to review every dispute
raised by customers, inspect evidence, and resolve with refund/partial/dismiss. See
[01-customer-portal.md §11](./01-customer-portal.md).

---

## 8. Support (manager view) — `/support`

The admin/manager tab lists tickets (same data source as users) and adds Resolve /
Escalate actions. See [01-customer-portal.md §12](./01-customer-portal.md).

---

## 9. Cross-portal touchpoints (admin)

| Feature | Reads from | Writes to | Consumed by |
|---|---|---|---|
| Dashboard | reporting (+ wallet/transfer aggregates) | reporting cache | — |
| KYC review | kyc | kyc (decision) | auth (tier), audit, notification |
| AML alerts | fraud-risk | fraud-risk (action) | audit |
| User management | auth | auth (status) | all portals (session/transactions blocked) |
| Merchant management | merchant | merchant (status) | customer directory, merchant portal |
| Audit | audit (event stream) | audit | compliance/ops |
| Disputes | dispute | dispute (resolution) | customer portal, audit |
| Support manager | support | support (resolve/escalate) | users |

## 10. Known limitations

- Dashboard "system health" panel is hardcoded, not live.
- `GET /v1/admin/dashboard` payload shape is consumed loosely (typed `Record<string,
  unknown>`) — KPIs may render empty until reporting-service populates `report_cache`.
- Support manager tab reuses the user's own ticket list rather than an admin-wide queue.
- AML action endpoints and alert generation depend on fraud-risk-service having
  processed `txn.completed` events.
